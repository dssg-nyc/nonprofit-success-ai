NYC-DSSG Partner Portal

Nonprofit Success AI

A CSM-grade lifecycle platform for every pro bono engagement DSSG NYC runs — a client portal backed by three focused AI agents, a shared skill/tool runtime, centralized evaluation, and a small set of shared deterministic services. The design deliberately separates reasoning from execution: AI recommends, summarizes, classifies, and drafts; application services own state, permissions, scheduling, contracts, tasks, and external side effects. This revision removes overlapping agent responsibilities, eliminates duplicate capability pipelines, and aligns the application to a shared Supabase identity/database foundation with GrantPilot before the shared-user pilot expands.

Every nonprofit enters through the same bottleneck

Today, intake runs on whichever volunteer has an hour free — not on a process. Nonprofits arrive with every level of data maturity, problem clarity, and capacity, and whoever picks up the email decides the bucket and the fit from scratch, every time. Nothing is captured or reused, so each new volunteer re-learns the same judgment calls — and the organizations with the least data maturity, who often need DSSG most, quietly fall through the cracks.

The system described here automates the repeatable half — routing, scoring, health monitoring, communications — and keeps a human in the loop for the judgment half: approving intake decisions, ratifying plans, and signing off on anything that reaches a partner.

Time back to volunteers

Triage and onboarding-prep move from a recurring, ad hoc task to a system that runs itself — freeing volunteer hours for the actual project work.

Better matches, faster starts

Every nonprofit gets a consistent readiness check and a bucket that fits, instead of whatever the on-call volunteer guesses that week.

Social impact through inclusion

Advisory is a real first-tier offering, not a rejection path — the earliest-stage nonprofits are never turned away.

Under $50/month to run. And human-in-the-loop by design — every agent drafts and recommends; a person approves anything that reaches a partner.

The Lifecycle

One journey, seven controlled gates

What a nonprofit experiences as a single journey is, underneath, two connected systems: a public, pre-account triage step, and a six-stage roadmap inside the portal once they're a client. Five agents reason; deterministic rules execute. AI agents attach to decision points; deterministic code owns execution and state transitions.

Public · pre-account · no login

In portal · authenticated · engagements/{businessId}_{stage}

Stage 0 — Public Intake

ScoutHITL L2 / L3

A prospective organization fills out a 10-question form at /apply — five to seven minutes, no account required. Scout scores the response into one of five buckets plus an independent readiness signal, then writes a single scout_intakes row holding the raw answers, its own routing output, and (later) a reviewer's decision.

Where Scout sits: entirely before the funnel — there's no logged-in user, and no Business or Engagement record exists yet. An admin works the queue at /scout/review and approves, edits, or rejects-and-redirects.

Stage 1 — Initial Meeting

ArchitectHITL L3

The kickoff call. Architect's 18-question Current State Assessment gets conducted live by staff (~30 minutes) — distinct from Scout's 5–7 minute public triage. The assessment scores five maturity dimensions and generates a charter plus a 90-day plan. Once staff approve the charter, it's populated into an Engagement Contract for the nonprofit's authorized rep to preview and sign.

Stage 2 — Budget Check

Pulse

Tracked as an engagement document with status (pending / in_progress / completed), free-text notes, and a budget_amount field. No agent owns this stage — Pulse flags a budget conversation that's stalled.

Stage 3 — Data Ethics Committee

Pulse

Same document pattern as Budget Check. Often described conversationally as one combined "budget/ethics check," but the roadmap treats them as two separate, sequential gates.

Stage 4 — Scoping

ArchitectProject Scoping

Where Architect's generated 90-day plan gets operationalized — build-basics, ship-one-deliverable, remediation-only, or accelerate, depending on the maturity score. Problem filtering and impact ranking is what Architect is doing here — one capability, not a separate hand-off.

Stage 5 — Hackathon Ready

Envoy ServicesResource Planning

Venue/food/tech logistics and Eventbrite-plus-social promotion are handled by the shared Operations and Communications Services, gated at L4 (human decides, agent assists), since all of it is partner-visible.

Stage 6 — Membership

ChronicleHITL L3

Chronicle's impact wrap-up: memos, case studies, and lessons that feed back into Scout's onboarding kits — turning this single engagement into institutional memory for the next one. This closes the loop the problem statement opened with.

Consent & Legal — the gate between Stage 1 and Stage 2. Once staff approve Architect's charter, it populates an Engagement Contract for the nonprofit's authorized rep to preview and sign in-app — typed name, checkbox, and a server-stamped timestamp (never the client's clock). The signed record is immutable: no update, no delete, no admin override. Stage 1 doesn't close, and Stage 2 doesn't unlock, until that signature is on file. See C4.G Contract & Consent for the interactive demo.

Partner Orgs

A serious response to a form, in days rather than weeks.

  • A plan sized to reality. An org with no data foundation gets a build-the-basics plan, not an ML project it cannot support.
  • Communication that does not over-promise. Every partner-facing message is drafted by the system and approved by a human before it sends.

Data Diplomats

Arrive on Monday, be useful by Friday.

  • Navigate code you did not write. A structural index across DSSG repos — symbols, calls, impact paths — not just text search.
  • Inherit judgment, not folklore. The scoring rubrics and health thresholds are code with tests, so they can be read and challenged.

NYC-DSSG Staff

See the portfolio, not a pile of spreadsheets.

  • Health before the stall. Every engagement carries a status and the reasons behind it, computed at read time.
  • Approval where it matters. High-confidence routine calls act directly; everything else waits for a human.
  • An audit trail by default. Every model call is recorded with its version, inputs, and outcome.
C4.G

Contract & Consent Gate

server-stamped · immutable write

Once staff approve Architect's charter and 90-day plan at the end of Stage 1, the nonprofit's authorized representative formally accepts before the roadmap advances. That's a different kind of gate from anything else in this document — not staff overseeing an agent, but the client's own legal consent. SPECIFIED Δ9

Recommendation: preview and sign in-app, not download-and-email

Option A

Download, sign, email back

  • Zero build cost — works today with a PDF and a mailto link
  • Feels familiar to EDs used to wet-ink workflows
  • Relies on someone remembering to send it, and staff manually matching the reply
  • No automatic stage-gating — someone has to notice and flip the status by hand
Recommended Option B

Preview & sign in-app

  • No context-switch — reviewed and executed where the charter already lives
  • Server timestamp + typed name become part of an immutable record automatically
  • The signature event itself gates the Stage 1 → Stage 2 transition
  • Directly serves the stated goal: time back to volunteers

Best of both: keep a “Download PDF” button for the signer's records, and auto-email the fully executed document to the signer and to dssgnyc@gmail.com on sign. A typed-name-plus-checkbox e-signature with a server timestamp is generally sufficient under ESIGN/UETA — worth confirming with DSSG's counsel once the real contract text exists.

C2

Containers

zoom: separately deployable things

Four containers: a browser bundle, a function set, a managed database, and a scheduled indexer. The SPA reads Supabase directly under RLS using the anon key. /api exists for work the browser must not do: holding model keys and making LLM calls. The Codemap Indexer is the only process that runs outside a request — a GitHub Action on a cron, holding the service-role key, writing to code_symbols and code_edges. It is not a hosted deployable, so it does not violate the single-deployment constraint.

Why one deployment is a hard constraint, not a preference. A second deployable is a second thing to host, monitor, credential and hand off. The operating budget is under $50/month and the team is volunteers. The boundary rule — src/{model,schemas,guardrails,observability} may not import from agents/ or app/ — preserves the option to extract a shared package later without paying the cost now. The Codemap Indexer is the one exception: it is a GitHub Action, not a hosted process — no always-on worker, no infrastructure bill, no additional deployment to monitor. Every recurring job is a cron Action, not a service.

Provenance — where a sentence came from

Provenance is a data contract, not a UI feature. A badge reading "AI-generated" with no column behind it cannot answer where did this sentence come from? six months later — and that is the question asked when a partner disputes something in a charter. Four kinds of content, carried in the schema:

KindMeaningTrust
Verified factSourced directly from system or user inputAuthoritative
Deterministic inferenceComputed by stated rules — compositeSignal(), the maturity rubric, the health taxonomyReproducible by hand
AI interpretationGenerated by a named agent through the gatewayRequires approval before it reaches a partner
Human decisionApproved, edited, or rejected by staffAuthoritative; supersedes the above

Columns on any table holding model-generated content — architect_assessments, chronicle_drafts, communications, scout_intakes: source_type, generated_by, model, model_version, prompt_version, run_id, approved_by, approved_at (GAP Δ20).

The chain has to be traversable: agent_run → proposal → human edit → approval → state transition → external effect. Every hop is a row naming the previous one. Given a sentence in a partner email, that answers which model wrote it, on what prompt version, who edited it, who approved it, and which transition it accompanied. Break any link and the system can no longer explain itself. Two rules that are easy to violate: a human edit versions rather than overwrites (otherwise the record shows a person authoring text a model drafted), and approved_by is set by the approval path, never by the agent — same rule as hitlTier. This lands with Δ4: retrofitting provenance after content exists means backfilling columns nobody can populate, because the runs are gone.

The partner is the only principal whose write surface exceeds its authority. Every other row is read-only or server-side. That asymmetry is not a subtlety — it is a live hole: the owner-scoped write policies predate the state machine, so a partner org can mark itself hackathon_ready on day one, skipping budget, ethics and scoping. The subject of a gate is currently its own approver (Δ22). It is the one non-additive fix in the queue, because closing it breaks the portal's current write path.

Prompt content is a read surface. A model provider sees whatever a prompt includes, so prompt assembly obeys tenancy like any other read — never built from a query that was not itself RLS-scoped. Transcripts are restricted and never logged; same reasoning, applied to the logging sink instead of the model.

C4.S

Execution Semantics

the rules between components

No single component owns these, which is why they go unstated until something breaks. Every row is specified or explicitly deferred — silence is not an answer, because silence reads as "handled". A consequential command is any server-side operation that is externally visible or hard to reverse: a transition, an approval, a signature, a partner-facing send, a publish.

ConcernPositionState
Idempotency Every consequential command takes an idempotencyKey, unique per attempt; a replay returns the original result. Client-generated per user action, not per request, so a retry after timeout carries the same key. Without it a double-clicked Approve produces two approvals and two emails. SPECIFIED
Concurrency Partially deferred. No version columns, no optimistic check for interactive writes. One staff team, no concurrent-edit UI. The accidental backstop is unique (business_id, stage) — two transitions to the same stage give one success and one 23505 → 409. Not covered: two transitions to different stages race. Mechanism if it lands is SELECT … FOR UPDATE, not a version column. The Codemap Indexer is the scheduled writer that trips this trigger — it writes to its own tables (code_symbols, code_edges) with no overlap on engagement rows, so the deferral holds for the engagement domain but row-level locking for the indexer’s upserts must be addressed with Δ30. DEFERRED
Async boundary Realtime is UI synchronization, not a domain event bus. Row changes push to subscribed clients as a consequence of a write, never a step in one. No workflow step may depend on a client having received an event — that makes the business process depend on a browser tab being open. Direction is always command → transaction → state + event → commit → Realtime informs. SPECIFIED
Structured vs. blob JSONB for a flexible artifact stored and rendered whole (architect_assessments.plan, a draft narrative). Relational for queryable domain state. The test: if a query the product needs would have to reach inside the blob, it is not a blob — which is why milestones and tasks are tables. SPECIFIED

Failure taxonomy

stack/vercel-functions.md defines the four-rung ladder for endpoint failures — missing model key, bad JSON, invalid input, model failure. Consequential commands add the rows an endpoint ladder cannot see.

FailureBehavior
Guard unmet422, the unmet condition named. Never a silent no-op
Approval missing where required422, nothing written
Actor not authorized403, nothing written
Duplicate request (same key)200 with the original result — not an error
Concurrent write, same rowOne success, one 409. No partial state
Database unavailable mid-transactionPostgres rolls back. No half-applied command
Side effect fails after commitThe command stands. Logged, retried out of band, surfaced to staff — never rolled back
Approval service unavailable503. The command does not proceed unapproved

The last two rows are the ones most easily got wrong. A side effect that can roll back a committed legal signature is worse than a failed email — the Contract & Consent gate set that precedent and this generalizes it. An email that fails after a signature commits is an operational problem; a signature that vanishes because an email failed is a legal one.

Five agents, shared services, zero duplicate ownership

An agent is a named decision surface in the engagement lifecycle. It maps an unstructured input to a structured output and owns that judgment. Whether that judgment comes from a model call or a mechanical rubric is an implementation detail — two of the five never call a model at all, and are not placeholders for ones that will. One owner, one data model, one audit trail for every operational function.

The four rules every agent path obeys

1. Deterministic result always exists

Every agent path produces a usable result without a model call. The model enriches; its absence degrades, never blocks.

2. Failure signalled, never simulated

When data is insufficient the agent returns an explicit signal (not_ready, empty fields), never a plausible placeholder.

3. Deterministic path tested independently

The fallback has its own test suite, run in CI, unaffected by model availability or cost.

4. Tracing at the model-call boundary

The gateway writes agent_runs; the agent does not. One instrumentation point for every model call in the system.

C3.3

Pulse

engagement health · deterministic · no model

A named decision surface that maps engagement telemetry to a health verdict: on_track, at_risk, or stalled. Pulse never calls a model — and is not a placeholder for one that will. The old five-agent model defended this explicitly: whether judgment comes from a model or a rubric is an implementation detail. Architect also never calls a model for scoring; neither is diminished by being deterministic.

Current state: Pulse currently reports at_risk for everything, because nothing writes engagement_events yet (Δ16). That’s honest — the no-history rule (R1) fires for the entire portfolio. The signal becomes useful the moment the event producer lands.

C3.4

Envoy

partner comms · occasion selection · drafting

The agent that owns partner-facing communication judgment: occasion selection, context assembly, and drafting. The communications send path owns the deterministic execution: rendering, delivery, retry, and provider adapters. The design’s own tiering puts partner-facing communication at L4 (its strictest oversight tier), and a capability warranting the strictest oversight is not a template renderer — it is an agent.

Staff-initiated was chosen over three candidates. Nothing fires autonomously. Envoy drafts on staff request, presents the draft for review, and sends only after explicit approval. This is the safest of three designs evaluated (auto-send with override, auto-draft with approval, staff-initiated) and was selected because a partner-facing message from a volunteer program has reputational stakes that exceed the cost of a manual trigger.

C4.H

Human-in-the-Loop Tiers

the design constraint, not an add-on

Every agent action maps to one of four levels. Escalation increases with partner-facing stakes — nothing reaches a nonprofit partner without the appropriate level of human judgment in the loop. This is staff overseeing an agent; it's a different axis from the Contract & Consent gate (C4.G), which is the client's own consent, not a staff review.

L1

Agent acts, human notified

Internal health signals, telemetry, non-partner-facing housekeeping
L2

Agent acts, reversible

Scout high-confidence classification and other low-risk internal transitions
L3

Agent drafts, human approves

Architect plans · Chronicle impact memos · low-confidence recommendations
L4

Human decides, agent assists

Partner-facing communications, commitments, publishing, contracts, and consequential decisions

deriveHitlTier() is one switch over the whole roster — precisely so a model cannot grant itself a tier by living in its own file. The tier is derived server-side and omitted from every output schema; the model never sees or returns it. src/guardrails/hitl.ts.

C4.E

Evaluation & Quality Gates

deployment gate, not a dashboard

Every agent and shared skill must have a measurable quality contract. Deterministic tests first, model-based judges second, human review for consequential behavior. No prompt, model, skill, or tool change reaches production solely because a demo looks good.

LevelCheckExamplesRelease rule
Q0Schema / unit testsJSON schema validity, required fields, permissions, deterministic scoring, tool argument validationMust pass 100%
Q1Golden-set regressionCurated Scout intakes, CSA assessments, charter examples, impact summariesNo regression from approved baseline
Q2LLM-as-a-judgeCorrectness, groundedness, completeness, instruction adherence, toneMinimum score threshold + no critical failures
Q3Safety / adversarialPrompt injection, unauthorized data access, fabricated citations, PII leakageZero critical policy violations
Q4Human acceptancePartner-facing drafts, legal/contract artifacts, consequential recommendationsExplicit human approval before release
Q5Production monitoringLatency, failure rate, tool errors, override rate, approval rate, judge drift, costAutomatic alert / rollback thresholds

Judge design

A dedicated evaluator model or ensemble for rubric-based checks — never treated as ground truth. Judge outputs calibrated against human-labeled examples, versioned alongside the prompt/model under test, supplemented by deterministic assertions. For critical workflows: judge pass + human approval.

Offline eval

Run on every skill/prompt/model change against fixed golden datasets before deployment.

Shadow eval

Run a candidate model in parallel without affecting production decisions to compare quality and cost.

Online eval

Track real outcomes, staff overrides, partner corrections, and downstream completion rates after launch.

Team is not a third table. It is a classification of Knowledge documents. A registry with one consumer is a folder; Team content — who owns which repo, codemap pointers, review dimensions — is prose about people and repos. It retrieves through the same path as everything else.

Memory system — no external system, no proxy

Cognee, Mem0, Letta, and Zep/Graphiti were surveyed as candidate memory layers. Cognee was the strongest fit — native multi-user permissions, embedded deployment, code indexing built in — but the system any of them would bring (Postgres, RLS, document storage, auth) is already live in this repo’s Supabase project. Standing one up means a second database, a second identity model, and a second permission set to keep in sync with these.

A MemoryProxy — sitting in front of the model endpoint, injecting a memory-search tool into an agent’s tool list — exists to add memory to agents you cannot modify. Every agent here is one this repo writes, with its tool list defined in src/agents/. Memory is adding a tool, not intercepting a protocol, so there is no proxy.

Chat memory extraction (L1–L3 from conversation history) is out of scope. The operational cost is too high for a volunteer-maintained system. Granola meeting summaries ingest as documents instead — the summary already exists, at zero LLM extraction cost, with none of the multi-writer consolidation problem raw conversation memory would carry.

Retrieval architecture

One retrieval core (src/knowledge/retrieval.ts), two consumers. No proxy, no separate service.

/api/knowledge-search

The agents’ tool. Runs inside Vercel Functions alongside the agent that calls it. No extra hop.

/api/mcp

A thin read-only MCP endpoint for volunteers in Claude Code. Holds no retrieval logic and never writes.

Everything except Granola is batch or manual. Granola meeting summaries arrive as webhooks → /api/knowledge-ingest → documents → chunk + embed → document_chunks. Service-role key, shared-secret verified, org_id resolved from the meeting’s engagement.
